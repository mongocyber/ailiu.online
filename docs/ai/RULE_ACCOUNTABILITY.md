# Rule Accountability Matrix

This Matrix accounts for the hard rules in `AGENTS.md` and `docs/OPERATIONS.md`.
Guidance without a listed enforcement channel is advisory.

| Rule | Trigger | Enforcement Layer | Evidence | Failure Action | Removal Condition |
| --- | --- | --- | --- | --- | --- |
| R1 — Follow current authority and exact scope | Any task or edit | Semantic and Human | Scope-matching active native task or explicit owner task-authorization record, Git status, baseline-to-candidate diff, and native-platform evidence; completed or adjacent Issues and the legacy capsule are background only | Stop or remove the out-of-scope change | A later active task or owner authorization explicitly changes the authority or scope |
| R2 — Keep content in its source of truth | Any copy or project-data change | Semantic | Diff review shows content changes only in `src/content.ts` | Move the content to its canonical source or stop | An authorized architecture change replaces that source |
| R3 — Preserve the motion mechanism | Any reveal or parallax change | Executable and Semantic | Browser behavior, desktop/mobile screenshots, and exact diff | Restore the rAF/watchdog pattern or stop | An authorized task replaces the motion architecture with verified evidence |
| R4 — Use one state-preserving verifier | Any implementation or verification claim | Deterministic and Executable | Successful native verifier output with clean-entry and clean-exit checks over tracked, staged, and untracked files | Treat the candidate as unverified and fix the verifier or failure | The repository adopts a different single native verification entry |
| R5 — Verify user-visible changes visually | Any frontend behavior or presentation change | Executable and Human | Desktop and mobile preview screenshots bound to the candidate | Keep the change incomplete until both views are checked | The project no longer has a visual frontend |
| R6 — Obtain owner approval for gated changes | Any listed real-world, dependency, private-data, delete, or reset action | Human | Explicit approval naming the action and scope | Stop before execution | The action no longer has the listed impact and is reclassified with evidence |
| R7 — Keep authority levels separate | Any move from read through release or any production action | Human | Separate approval for the requested level; explicit owner approval for production | Stop at the currently authorized level | The owner explicitly changes the authorization policy |
| R8 — Keep task scope and worktrees isolated | Any candidate edit or authority-level change | Deterministic, Semantic, and Human | Authorized-path and authority-level comparison, exact baseline-to-candidate diff, owner-worktree readback, and independent review when required | Fail closed, remove scope drift, and return to the owner | Current authority explicitly expands the paths or authority level |
| R9 — Keep the import neutral and avoid unsupported model claims | Any `CLAUDE.md` change, external-model call, or compatibility claim | Deterministic and Semantic | Native verifier output and exact-revision review | Restore import-only content, stop the call, or withdraw the claim | New task authority plus exact-revision proof permits the difference |
| R10 — Account for every hard rule | Any hard-rule or Matrix change | Deterministic and Semantic | Native verifier checks for `R` rows, exact `R`/`O` source-to-Matrix ID parity and six-field assertions, and independent review | Fail verification or demote unenforced text to advisory guidance | An authorized policy replaces rule accountability |
| R11 — Preserve native review evidence | Any reviewable change | Deterministic and Semantic | Completed checklist in the actual native PR description and review record; verifier proves only that template fields exist | Keep review incomplete until the checklist is completed, or restore missing template fields | The native review platform enforces equivalent evidence |
| R12 — Require independent exact-candidate review | Any medium/high-risk completion or semantic acceptance | Semantic | Fresh findings-first review bound to the full candidate SHA | Keep semantic acceptance pending | The authorized review policy changes |
| R13 — Use a supported Node.js version | Any setup or verification run | Executable | Native verifier output records a Node.js major version of 20 or newer | Stop verification and use a supported Node.js runtime | The project toolchain explicitly adopts a different minimum |
| O1 — Re-read operational truth sources | Any operational claim or action | Semantic and Human | Fresh Git, GitHub/Linear, Vercel, and HTTP/browser readbacks appropriate to the claim; no copied deployment ID is treated as current | Mark the fact `UNKNOWN / NOT VERIFIED` and stop any dependent action | The repository adopts an equivalent current-state evidence surface |
| O2 — Enforce authority and stop lines | Before push, PR, merge, production, rollback, settings, dependency, secret, data, destructive, or owner-worktree action | Semantic and Human | Scope-matching active Issue or explicit owner task authorization plus separate approval for the exact authority level and action | Stop before the action; do not expose secrets or infer authorization | The owner explicitly replaces the authorization policy |
| O3 — Bind Preview to the exact candidate | Any Preview verification claim | Semantic and Human | Vercel project, UI environment, raw API target, Git SHA, ref/branch, PR, READY status, and risk-based browser checks all bound to one deployment | Keep Preview `UNKNOWN / NOT VERIFIED` and stop promotion | The hosting platform provides an equivalent stronger binding |
| O4 — Bind Production to the exact merge | Any Production deployment or readiness claim | Semantic and Human | Separate Production approval; readback of project, Git/main source, merge SHA, production target, READY status, and production alias for one deployment | Stop release or mark Production `UNKNOWN / NOT VERIFIED`; do not start an unauthorized manual deployment | The hosting platform or release policy adopts an equivalent stronger binding |
| O5 — Complete production smoke without evidence substitution | Any production validation or live claim | Executable, Semantic, and Human | Deployment binding, required HTTP results, desktop/mobile browser checks, console results, and response-policy checks recorded separately | Stop the release, enter incident handling, and keep failed or missing checks unverified | The production surface or approved validation contract changes |
| O6A — Prove the Analytics candidate is deployed | Any claim that a deployment contains Analytics | Semantic | Exact deployment metadata bound to an approved Git SHA whose source and dependency diff contains the Analytics integration | Record `UNKNOWN / NOT VERIFIED`; do not advance the Analytics claim | Analytics is removed or an equivalent artifact-provenance check replaces this gate |
| O6B — Read back the Analytics setting without changing it | Any claim that Web Analytics is enabled for an environment | Human | Time-stamped, read-only Dashboard readback for the exact project and environment | Record `UNKNOWN / NOT VERIFIED`; obtain separate owner approval before any setting change | Analytics is removed or the platform provides equivalent immutable configuration evidence |
| O6C — Prove the page requested the Analytics script | Any claim that an exact deployment loads Analytics | Executable and Semantic | Browser Network/console evidence for the target page showing a successful script request, URL, environment, deployment ID, time, and new-error count | Record `UNKNOWN / NOT VERIFIED`; do not treat source, DOM, logs, or direct endpoint access as proof | Analytics is removed or the client integration adopts an equivalent verified transport |
| O6D — Prove a real Production pageview in a bounded window | Any claim that Production Analytics is live | Semantic and Human | Predeclared `T0`–`T1`, real production-domain visit after release, and time-stamped Dashboard result filtered to Production, domain, and window | Record `UNKNOWN / NOT VERIFIED`; do not infer ingestion from earlier Analytics gates | Analytics is removed or the approved product metric and evidence contract changes |
| O7 — Keep rollback owner-gated and revision-bound | Any proposed or actual Production rollback | Semantic and Human | Incident evidence, exact previously verified READY Production deployment and SHA, owner approval naming that target, alias/target readback, and repeated production validation | Stop if the target or approval is missing; do not use DNS, deletion, reset, force push, or history rewrite as rollback | The owner adopts a different reviewed rollback policy |
| O8 — Triage incidents without unauthorized repair | Any availability, wrong-version, page-regression, Analytics, DNS, domain, or certificate incident | Semantic and Human | Evidence separating deployment, alias/domain, HTTP, browser, Analytics, and DNS causes plus approval for any gated remediation | Preserve evidence, stop new release actions, and request the smallest authorized rollback or fix decision | An approved incident-response policy replaces this section |
| O9 — Keep monitoring claims honest | Any monitoring, alerting, uptime, auto-repair, or operational-coverage claim | Executable, Semantic, and Human | Repository tests and native-platform evidence remain separate; repo-local fixture success is labeled not installed and not live, and absent capabilities remain explicitly unverified | Withdraw the claim, keep manual production validation required, and obtain owner approval for any new service | Verified monitoring replaces the manual gate and every affected Matrix row is updated |
| O9A — Classify checks from raw facts | Any DNS, TLS, HTTP, content, or deployment-reference result | Deterministic and Executable | Offline raw-fact fixtures, fixed failure priority, canonical HTTPS routes, exact HTTP 200 and content markers, bounded transport budgets, and explicit `UNKNOWN_NOT_VERIFIED` runtime status for the non-health deployment reference in the native verifier | Fail verification or record the result as `UNKNOWN / NOT VERIFIED`; never let a later check or configured reference overwrite an earlier-class failure | The approved checker adopts an equivalent deterministic classification contract |
| O9B — Persist one logical incident and recovery | Any failure threshold, alert, deduplication, retry, recovery, or heartbeat claim | Deterministic, Executable, and Semantic | Cross-process state-machine and strict offline transport-stub tests prove three consecutive failures, immutable state-v2 alert/recovery snapshots, stable event IDs, pending-alert-before-recovery order, same-ID 2xx retries, continued-failure deduplication, independent repeated incidents, all-check recovery, heartbeat after every completed cycle, corrupt-state rejection, and lock safety | Fail verification, preserve the last valid state, and withdraw any exactly-once claim unless receiver idempotency is separately verified | An approved incident engine provides equivalent durable and idempotent semantics |
| O9C — Keep the local monitor template inert and testable | Any repo-local checker, fixture, environment example, service, or timer change | Deterministic and Executable | Tracked regular-file modes, shell syntax, offline fixture suite, ancestor and dangling-symlink probes, direct transport process cleanup, 40/50-second external-budget assertion, explicit absence of a standalone whole-cycle guarantee, secret canary, section-aware systemd assertions, and negative mutation probes run through the native verifier | Fail verification, remove unsafe template content, and keep the candidate not installed and not live | The repository adopts an equivalent verified packaging and test surface |
| O9D — Gate installation and live monitoring evidence | Any VPS install, systemd enable/start, secret placement, journald, heartbeat, live alert, or monitoring-live claim | Semantic and Human | Separate owner approvals plus target VPS/user/systemd inventory, secret-storage and provider decisions, unit/timer/reboot/journal readbacks, current deployment provenance, receiver idempotency, and independent heartbeat evidence | Stop before the gated action or keep the capability `UNKNOWN / NOT VERIFIED`, not installed, or not live | The owner approves an equivalent activation policy backed by stronger native evidence |
| O10 — Preserve the minimum operation record | Every candidate, release, validation, incident, or rollback record | Semantic and Human | Time, actor, authorization, full revisions, changed paths, checks, review, deployment binding, smoke/Analytics stage, failures, rollback target and approval; missing fields use `UNKNOWN / NOT VERIFIED` | Keep the operation incomplete and do not backfill expected results as facts | An approved evidence system captures equivalent fields durably |
